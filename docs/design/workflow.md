# 起動

1. `Program` が Velopack の内部フックを UI、昇格、多重起動判定より先に処理します。
2. Windows では旧スタートメニューを移行し、必要なら署名済み PerMachine MSI への移行・既知の誤配置修復を行います。
3. `asInvoker` で開始した通常プロセスを `runas` で自己昇格してから `SingleInstanceGuard` を取得します。
4. `App.axaml.cs` が OS に応じたサービスを DI 登録し、`MainWindowViewModel` と画面を構築します。

この順序により、Velopack のフックを昇格要求で壊さず、非昇格プロセスが単一起動ロックを保持したまま
昇格後プロセスを妨げる状態を避けます。macOS はアプリ全体を昇格せず、DNS 変更とキャッシュ消去だけを
`osascript` 経由で管理者実行します。

Release 版は UI 作成前にプロセス AppUserModelID を `velopack.Shisui` に設定し、
インストール済みショートカットと一致させます。Debug 版はこれを省略し、
Windows が開発版のタスクバーアイコンを製品ショートカットから解決することを避けます。
ネットワーク変更はシステム全体に及ぶため、実行時昇格は Debug 版でも行います。

## おまかせの起動境界と再確認

Windows のおまかせ設定は、最初の設定変更前に System ログの最新 RecordId と同イベント XML の SHA256 を実行中だけ保持します。さらに Kernel-General 12 / Kernel-Boot 27 の RecordId と XML SHA256 の組を起動指紋として取得し、再確認待ち・再起動必須フラグとともに保存します。境界・指紋を取得できないか保存に失敗した場合は、ネットワーク設定の変更を開始しません。

次回のアプリ起動時は、共有リース内で保存した起動イベントを再照合します。同一指紋は SameBoot、保存した両レコードの同一性を確認でき、整合した新しい 12/27 の組が旧組より後にある場合だけ ConfirmedNewBoot、それ以外は Unknown です。古い 27 との混在、起動の再開・高速起動（BootType が 0 以外）、欠落・再利用・ログ消去・指紋取得不能は再起動の証拠にしません。時刻の差だけでも再起動とは判定しません。

SameBoot と Unknown は、問い合わせやキャッシュ再構築をせず確認待ちを維持します。旧版の pending だけは互換として一度確認し、新版の再起動必須・指紋欠落は Unknown と区別します。ConfirmedNewBoot の後は、新しい検査境界でキャッシュ再構築と名前解決・静的検査を最大 2 回行い、検査成功と解除の保存が成功した場合だけ待機を解除します。保存に失敗した場合はメモリー上の待機も戻し、次回の自動確認は保証しません。NRPT・hosts・証明書・TLS・プロキシ設定の削除や書換え、Tailscale の再起動、イベント消去、旧設定の復元は行いません。
