# 実機での検証結果

ここに記す結果は、記載の 1 台・OS ビルド・回線での確認に限ります。他の環境の改善を示すものではありません。

## 上り速度の制限

条件は Wi-Fi、Windows 11 build 26300、夜間 1 回、BBR2・pacing=always 適用済みです。

| 条件 | NIC 送信 | 負荷時 ICMP（1.1.1.1） |
| --- | --- | --- |
| 制限なし（4 接続・各 10 秒） | 36.8〜37.2Mbps | p50 83〜119ms / p90 161〜169ms / 損失 5〜7 件 / 約 50 件 |
| 28Mbps（`ActiveStore`） | 28.8〜28.9Mbps（設定値の約 1.03 倍） | p50 17ms / p90 21〜25ms / 損失 2〜3 件 / 約 100 件 |

- UDP 60Mbps は、制限ありで NIC 28.3Mbps、なしで 59.2Mbps でした。アプリ側の平滑制限では p90 が 145〜160ms から 13〜16ms に下がり、curl の間欠制限では改善しませんでした。
- ポリシーは作成直後から有効で、削除で戻り、再起動で消えます。毎回の読み戻しで残存 0 を確認しています。Windows PowerShell 5.1 でも作成・読み戻し・削除と、条件が保存されないことを確認しました。
- 計測サービス（`UplinkMeasurementService`）の実回線完走（管理者、別の時刻に 1 回）: 無負荷 p90 11ms、容量 36.9Mbps、提案 35.0Mbps（95%）。④ の p90 はなし 160/163ms に対し、あり 25/24ms、損失はすべて 0%、アプリ送信と NIC 送信の差は 2.5〜6.3%。送信 456MB・184 秒で、終了後の試験用は残存 0 件でした（同じ 1 台・別の時刻に 1 回）。
- 実アプリ（管理者、同じ 1 台）では、計測→適用→読み戻し→実測（上限 34.2Mbps に対し NIC 34.1Mbps、p90 24ms）→終了しても維持→再起動相当（ポリシーを外して起動し直し）の再適用→解除、計測の中止、強制終了後の起動時の試験用削除を Debug 版で確認しました。Native AOT 公開物（署名・MSI なし）では、計測の完走、他ポリシーがある場合の拒否、強制終了後の試験用削除、保存済み設定からの起動時適用、解除を確認しました（[この上限を適用] のクリックは Debug 版だけ）。
- ③ の合格線 +15ms を ④ にも使っていた間は、3 回中 1 回が ④ で「改善なし」になりました。その回の区間値は記録しておらず、落ちた条件（遅延か損失か）は未確認です。変更後の 2 回は合格しましたが、変更の効果を示すものではありません。現在は不合格時に区間ごとの p90 と損失を表示します。
- 未検証: 署名済み MSI での動作、実際の PC 再起動後の再適用、回線を切り替えたときの解除・再適用、ログオフ・更新再起動時の後始末、他の回線・時間帯・有線での効果。

## TCP

- ペーシング: 有線・BBR2 固定の off/always/off 比較では、中央値の一貫した改善はなく、Upload P95 は改善側でした。
- ACK 頻度（2026 年 10 月 24 日、Windows 11 build 26300・Wi-Fi、A/B/A2 各 3 試行）: 受信から ACK 送信までの時間の中央値の平均は 44.665ms → 0.125ms → 44.696ms でした。各段階の実再起動と設定値を照合した TCPIP 層の観測で、即時 ACK と既定の ACK の比較ではなく、ACK 頻度の A/B は未実施です。他の NIC・ビルド・ゲームや ping への効果、上り混雑時の影響は未測定です。
- RTT・ジッター・損失・フレーム時間の比較測定は、このプロファイルでは未実施です。
