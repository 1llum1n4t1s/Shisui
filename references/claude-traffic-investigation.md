# Claude 通信のパケット解析と「おまかせ高速化設定」候補（2026-11-15）

## 結論

- **Claude までの経路・TCP 品質には、OS 設定で詰める余地がほぼない。** 接続先は Cloudflare 東京（NRT）エッジで、ハンドシェイク約 9 ms、再送率 0.01〜0.02%、受信窓枯渇なし。応答の待ち時間の大半はエッジより先（Anthropic 側の処理・推論）で、ストリーミング受信の間隔（中央値約 37 ms）もトークン生成の速さで決まっている。
- **ネットワーク側で唯一効いているのは上り帯域。** Claude Code は会話の文脈を毎回送るため、1 回の依頼で 1 MB〜4.2 MB を送る場面があった。上りは 1 本でも 4 本同時でも合計 32〜38 Mbps で頭打ちになり、4.2 MB の送信だけで約 1.1 秒かかる。これは回線（または Wi-Fi・ルーター）の上り容量で決まり、Windows の TCP 設定では増やせない。
- **大きな送信中は上りに滞留が生じる。** 送信中バイト数が増えるほど ACK 遅延が伸びる（下表）。同時に動くゲーム・通話・他の Claude セッションの遅延を一時的に悪化させ得る。ルーター側の待ち行列が主因とみられ、Shisui が直接制御できる設定ではない。
- 品質（応答内容）は通信路では変わらない。通信由来の品質問題は切断・中断だけで、今回の観測では再送・リセットに異常はなかった。
- 以上から、**既存の固定設定へ新しい変更を足すことは推奨しない**。追加するなら、読み取り専用の診断（候補 A）を先に入れ、変更系は比較実験で効果が再現した場合だけ検討する（候補 B）。

## 測定条件と限界

- 日時: 2026-11-15 19:30〜19:50 JST（夜間 1 回のみ）。Windows 11 Pro build 26300、Wi-Fi 5 GHz / 802.11ax、リンク 2402 Mbps、RSSI -40 dBm。DNS は Cloudflare（DoH）、TCP 5 テンプレートは BBR2、pacing=always、ECN=enabled（おまかせ高速化設定の適用済み状態）。
- 対象: `api.anthropic.com` / `claude.ai`（どちらも 160.79.104.10 / 2607:6bc0::10、Cloudflare 経由）。Claude デスクトップアプリと Claude Code の複数セッションが同時に動いていた。この調査セッション自身の通信も含む。
- 捕捉: `pktmon` で 120 秒 × 2 回（1 回目 NIC 層のみ、2 回目全コンポーネント）。先頭 128/160 バイトのみ記録し、TLS 本文は保持していない。1 回目は Wi-Fi ドライバ層で受信が 802.11 暗号化のままだったため、受信側の指標は 2 回目のみ。
- 2 回目は同一パケットが複数コンポーネントで記録されるため、同一ヘッダー（TSval を含む）の 50 ms 以内の再出現を重複として除いた。
- OS・Shisui の設定変更、実装変更は行っていない。上り速度の比較は Cloudflare の速度測定エンドポイントへの 40 MB の 0 埋めデータ送信で、Claude の接続先とは別ホスト。単一回の測定であり、時間帯による変動は未確認。

## 経路

| 項目 | 結果 |
| --- | --- |
| Cloudflare エッジ | NRT（両ホスト・IPv4/IPv6 とも） |
| ICMP RTT | IPv4 平均 11.6 ms / IPv6 平均 9.6 ms（各 20 回、損失 0） |
| 経路 | 宅内ルーター → ISP 内 2〜3 ホップ → Cloudflare → 終点。7〜9 ホップ、約 9 ms |
| TCP ハンドシェイク | 8.5〜13 ms |
| VPN・プロキシ | 経由なし（Tailscale は導入済みだが経路外、WinHTTP は直接接続） |
| TLS | TLS 1.3 / X25519 |

クライアントは IPv6 と IPv4 を同時に接続し（Happy Eyeballs）、IPv6 側が採用される。捨てられた IPv4 側でサーバーが約 1 秒後に SYN-ACK を再送するが、利用中の接続の遅延ではない。IPv6 を優先・無効化する設定変更の根拠にはならない。

## 上り送信の分解

送信中バイト数（ACK 待ち）別の、データ送信から対応する ACK までの時間。再送分は除外し、ACK 番号が一致する送信だけを数えた。

| 送信中バイト | 件数 | 中央値 | p90 | p99 |
| --- | ---: | ---: | ---: | ---: |
| 4 KB 未満 | 526 | 9.3 ms | 12.4 ms | 64.1 ms |
| 4〜32 KB | 4,433 | 9.5 ms | 12.8 ms | 30.0 ms |
| 32〜128 KB | 7,990 | 17.6 ms | 28.6 ms | 49.5 ms |
| 128〜512 KB | 5,147 | 60.0 ms | 132.6 ms | 214.4 ms |
| 512 KB 以上 | 212 | 195.3 ms | 210.4 ms | 217.0 ms |

単発送信では ACK 遅延は RTT とほぼ同じで、サーバーの遅延 ACK による水増しではない。送信中バイト数に比例して遅延が増えるため、上りの律速点に待ち行列ができている。帯域遅延積は約 36 KB（32 Mbps × 9 ms）だが、実際の送信中バイトは 512 KB を超えることがあり、BBR2 でも滞留を抑えきれていない。律速点が Wi-Fi・ルーター・ISP 上りのどこかは、有線比較をしていないため未確定。

100 KB を超える送信バーストは 35 回。主な例:

| 送信量 | 送信時間 | 実効速度 | 送信完了から最初の応答まで |
| ---: | ---: | ---: | ---: |
| 約 4.2 MB（6 回） | 1.03〜1.39 秒 | 24.8〜33.6 Mbps | 617〜1,301 ms |
| 約 1.0 MB（多数） | 0.25〜0.37 秒 | 23〜35 Mbps | 740〜1,011 ms（1 回 7.3 秒） |

全体ではサーバー待ちが中央値 831 ms / p90 1,052 ms、送信時間が中央値 250 ms / p90 1,080 ms。**大きな依頼では応答待ちの 2〜6 割が上り送信時間**になる。

上り速度の切り分け（Cloudflare 速度測定、40 MB）: 1 本 32.3 Mbps、4 本同時は合計 38.2 Mbps（各 8.4〜10.7 Mbps）。1 本でほぼ上限に達しており、TCP の 1 本あたりの制限（窓・輻輳制御）ではなく経路全体の上り容量が律速。無負荷 ping は中央値 9 ms、送信中は中央値 10 ms / 最大 28 ms だったが、送信 10 秒に対し ping は約 25 秒かかり負荷中の標本は 4 割程度のため、上表の実通信の結果を優先する。

## 「おまかせ高速化設定」への組み込み候補

### 候補 A（推奨・読み取り専用）: AI サービス接続診断

自動最適化画面に、Claude などの API 型 AI サービス向けの診断を追加する。変更は行わず、律速点と「変更不要」を利用者に示す。

1. 対象ホスト（既定は `api.anthropic.com`）の名前解決、IPv4/IPv6 別の RTT、TCP ハンドシェイク時間、Cloudflare `/cdn-cgi/trace` のエッジ（`colo`）を取得する。エッジが国外になっている場合や、VPN・プロキシ経由の場合に警告する。
2. 上り速度と負荷時遅延を同時に測る。送信中に十分な数の遅延標本を取り、無負荷との差を「上りの滞留」として表示する。送信先は利用者に明示し、0 埋めデータのみ送る。
3. 「1 MB の依頼を送るのに約 X 秒」の目安を表示する。上りが律速の場合は、有線接続・ルーターの QoS/SQM 設定・回線の上り容量を確認するよう案内する。Shisui はルーター設定を変更しない。
4. 既存の Ping/Traceroute（`INetworkDiagnosticsService`）を再利用できる。パケット捕捉は管理者権限と大量のログを要するため、診断の既定には含めない。

### 候補 B（保留・比較実験が前提）: 大きな送信時の滞留抑制

送信中バイトが帯域遅延積の 10 倍以上に膨らんでいるため、送信側で滞留を抑えられる余地はある。ただし効果は未検証で、次の比較で再現した場合だけ設定候補にする。

- 比較対象は一度に一変数: `pacingprofile`（always / off）、輻輳制御（BBR2 / CUBIC）。同じ 4 MB 送信で、送信時間・送信中 ACK 遅延の p90・並行する ping の遅延を各 5 回以上比べる。
- 上り容量が律速であれば、送信時間はほぼ変わらず、改善するのは並行通信の遅延だけと予想される。Claude の応答時間の短縮を目的にした採用はしない。
- ルーター側の待ち行列が主因なら、PC 側の設定では解消しない。

### 不採用（根拠なし）

- ECN の変更: サーバーが ECN を交渉しないため効果がない。
- IPv6 の無効化・IPv4 優先: 両系統とも同じエッジ・同程度の RTT。
- DNS 変更: 現在の Cloudflare DoH で東京エッジに到達しており、変える理由がない。
- QUIC/HTTP/3 の禁止: 一部クライアントが使用中。禁止による改善の根拠はない。
- `TcpAckFrequency`、受信窓自動調整、RSC 等の受信側調整: 受信は 1 本あたり数 KB/秒〜数十 KB/秒のストリーミングで、再送・窓枯渇もなく、律速していない。
